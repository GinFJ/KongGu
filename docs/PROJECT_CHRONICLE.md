## 序言

空谷不是从一开始就定型的产品。

它先以 V0.1 的桌面程序起步，随后尝试过本地 Web 形态，也曾为了收缩维护面而彻底移除桌面端。经过对实际使用场景的重新确认，项目最终回到“完全离线的 Windows 桌面工具”这条主线，并逐步把重点从“能够识别课表”推进到“能够给出可信、可复核、可用于真实排班的结果”。

空谷属于青禾计划系列项目。它面向中英合办及中外合作办学场景，解决多人中方、英方课表收集与合并中大量重复、耗时、低价值的人工劳动。

项目最核心的业务判断始终是：

> 同一成员只有在中方课表和英方课表中都没有课程占用，才算真正空闲。

本志不只是功能清单。它记录项目为什么改变、每个阶段解决了什么问题、哪些道路被尝试后放弃，以及空谷如何从一个可运行的工具逐步演变为强调离线、可信、可审计的业务系统。

## 二、项目总览

### 2.1 项目身份

| 项目 | 记录 |
| --- | --- |
| 中文名 | 空谷 |
| 英文名 | Konggu |
| 所属计划 | 青禾计划 |
| 主要场景 | 中英合办、中外合作办学中的多人课表汇总与排班 |
| 核心输入 | 多名成员的中方、英方课表 PDF |
| 核心处理 | 文本层提取、离线 OCR、版式识别、课程结构化、中英占用合并 |
| 核心输出 | 可复核的集体空课结果与 Excel |
| 当前运行形态 | Windows 离线桌面应用 |
| 当前技术主干 | Tauri + Vite/TypeScript + Python sidecar |
| 数据原则 | 本地处理、异常显性、拒绝无依据猜测 |

### 2.2 项目使命的形成

早期的空谷更接近“多人课表 PDF 解析与空课表生成工具”。随着真实业务场景被不断澄清，项目定位逐步收紧为：

> 为中英合办学生组织提供离线的双课表合并能力，把负责人从收集、查看、比对和统计课表的重复劳动中释放出来，同时让缺失、冲突和识别失败能够被看见、被复核。

这一定位改变了项目的评价标准：功能数量不再是首要目标，结果是否可信、错误是否可见、真实样本是否能稳定处理，成为后续迭代的核心。

## 五、第二纪：本地 Web 探索与 Web-only 收缩

### 5.1 为什么尝试 Web

本地 Web 界面提供了比传统桌面 GUI 更灵活的布局、交互和任务展示方式。FastAPI 路由、任务管理器、静态资源和结果页面在这一阶段建立起来，证明核心业务可以脱离原始桌面窗口运行。

这次探索带来了两个长期收益：

1. 界面不再与解析核心强绑定；
2. 任务状态、文件导入、处理和结果展示开始具备清晰边界。

### 5.2 2026-06-20：主动做减法

6 月 20 日，项目进行了集中治理：

- 更新 Web 端素材；
- 删除重复图片和无实际代码的占位包；
- 清理旧分支；
- 将默认分支统一为 `kongguV0.1`；
- 删除当时的 CustomTkinter 桌面端和桌面打包依赖；
- 将 README 改为符合当时 Web-only 状态的双语说明。

提交 `69021fa` 共涉及 28 个文件，约为 154 行新增、2168 行删除。它代表一次明确的收缩：当时项目选择保留本地 Web 入口，彻底放弃旧桌面客户端，而不是长期维护两套界面。

桌面测试随桌面代码一起移除后，历史测试记录为 `45 passed, 1 warning`。

### 5.3 这条路线为什么没有成为终局

Web-only 是一次有价值的架构试验，但它没有完全满足最终产品需求：

- 普通使用者更需要直接安装和打开的 Windows 软件；
- 本地服务的启动、端口和浏览器环境增加了使用门槛；
- OCR 模型、Python 运行时和配置需要统一封装；
- 项目强调离线和个人课表隐私，桌面安装包更符合交付预期。

因此，7 月的桌面化不是简单地恢复旧 GUI，而是在分层架构基础上选择了新的桌面技术路线。

## 六、第三纪：离线 Tauri 桌面端重建

### 6.1 2026-07-07：技术路线转折

提交 `7985d61` 将项目转换为离线 Tauri 桌面应用。这是空谷历史上最大的一次产品形态转折。

新结构为：

```text
Tauri Windows 桌面壳
  -> Vite / TypeScript 前端
  -> Python sidecar 命令桥
  -> app/services 工作流
  -> core/schedule_core 解析核心
  -> 本地 OCR、缓存、配置和 Excel
```

旧的 FastAPI Web 路由、模板和静态页面被移除；Python 解析能力没有被重写，而是通过 sidecar 继续复用。这样既保留了 Python 在 PDF、OCR 和 Excel 处理上的优势，又获得了现代桌面界面的安装、交互和资源封装能力。

### 6.2 完全离线成为产品底线

这一时期建立了完整的离线资源机制：

- 使用 PP-OCRv4 mobile 检测与识别模型；
- 通过 `config/ocr_models.json` 管理资源来源、大小和校验值；
- 生成 `resources/offline_manifest.json`；
- 将资源随安装包封装；
- 在用户目录中修复和维护可写资源；
- 默认禁止运行时在线下载 OCR 模型。

离线不只是技术特点，它回应了真实业务中的两个问题：课表包含个人信息，且软件不应依赖现场网络才能完成排班工作。

### 6.3 桌面工作流与交互完善

前端逐步形成明确的使用链：

```text
检查离线材料
  -> 选择 PDF
  -> 校验文件名与课表类型
  -> 解析中方、英方课表
  -> 查看空课预览
  -> 处理成员异常
  -> 导出 Excel
```

界面增加了五步流程条、状态标签、文件分组、缺失配对提示、成员检查、日志清理和友好错误显示。浏览器预览或非 Tauri 环境不再暴露底层 `TypeError`，而是提示用户需要在 Konggu 桌面端运行相关功能。

### 6.4 输入契约开始严格化

早期系统会在无法识别课表类型时做默认推断。随着产品目标从“尽量处理”转为“输出可信”，这一行为被取消。

正式形成的输入规则包括：

1. 文件必须是 PDF；
2. 文件名应包含真实成员姓名；
3. 文件名必须明确标出“中方”或“英方”；
4. 同一成员应同时提交两类课表；
5. 无法判断时拒绝解析，不静默猜测。

这意味着空谷开始把“拒绝不可靠输入”视为产品能力，而不是失败。

## 八、第五纪：真实样本、识别审计与可信结果

### 8.1 从“能跑”到“可信”

进入 7 月中旬后，项目的主要矛盾不再是界面或安装，而是不同来源的真实课表 PDF 能否被稳定识别。

这一阶段确立了长期原则：

> 错误的 Excel 只是症状，真正要修的是解析器、识别规则、输入预检和回归体系，而不是手工修改某一个输出文件。

### 8.2 文本层优先，OCR 作为回退

空谷的识别链并非对所有 PDF 直接做 OCR：

```text
PDF 文本层检查
  -> 文本质量与版式判断
  -> 可用时直接解析文本和坐标
  -> 不足时调用离线 OCR
  -> 必要时使用视觉版式回退
  -> 比较完整度和可信度
  -> 选择更可靠的结构化结果
```

这一路线降低了不必要的 OCR 成本，也保留了原生 PDF 文本层的精确信息。

### 8.3 专用版式与 Unicode 兼容

真实样本暴露出兼容表意字符问题：某些 PDF 中视觉上正常的汉字，底层编码并不是常用 Unicode 形式，导致版式特征匹配失败。

项目在版式检测前增加 NFKC 归一化，并在识别规则变化时提升解析缓存版本，避免旧缓存掩盖新规则效果。

随后形成了多类专用版式识别，包括：

- 中英合办英文 Web 课表；
- 本科全学期中文课表；
- 旧版中文 Web 课表；
- 英文周网格课表。

### 8.4 输入预检成为第一道质量门

真实样本库中还发现了两类不能交给解析器“自行处理”的坏来源：

- 使用“路人甲”等测试或占位姓名的文件；
- PDF 内容完全相同，但文件名对应不同成员的文件。

项目把这些检查前移到 PDF 导入层和审计工具中。坏来源不再被误记为自动通过，而是进入明确的待复核状态。

### 8.5 2026-07-23 解析基线

提交 `d860f7c` 固化了第一份正式的解析审计基线：

| 指标 | 基线值 |
| --- | ---: |

## 十二、关键决策录

### 决策一：空谷不是泛用课表软件

**结论：** 聚焦中英合办双课表合并和集体空课生成。

**原因：** 真实痛点不是个人看课表，而是负责人需要逐人、逐周、逐节核对中方和英方两套课表。

**影响：** 产品功能、README、输入契约、成员检查和输出结构都围绕这一场景收紧。

### 决策二：结果可信优先于识别覆盖

**结论：** 无法判断课表类型、身份或来源时拒绝猜测。

**原因：** 静默误判会直接污染空闲名单，进而影响真实排班。

**影响：** 未知类型、占位姓名、同内容异姓名和解析失败都必须显性进入错误或待复核状态。

### 决策三：优化程序，而不是手改结果

**结论：** 出现错误 Excel 时，修复解析器、输入预检、识别规则和回归测试，再从源课表重新生成。

**原因：** 手改一个文件不能解决下一批样本，也会破坏结果可追溯性。

**影响：** 真实样本库、审计 CSV、版式规则和回归基线成为解析迭代的主要依据。

### 决策四：文本层优先，离线 OCR 回退

**结论：** 先检查 PDF 文本层，只有在文本不足时才进入离线 OCR 或视觉回退。

**原因：** 原生文本层通常更快、更精确，OCR 应用于真正需要的样本。

**影响：** 识别链需要同时维护文本、坐标、OCR、视觉回退和完整度比较。

### 决策五：最终产品保持离线 Windows 桌面形态

**结论：** 使用 Tauri 桌面壳封装前端、Python sidecar 和 OCR 资源。

**原因：** 降低普通用户使用门槛，保护课表隐私，并减少对浏览器、本地服务和网络的依赖。

**影响：** 发布流程必须验证 sidecar、前端、Tauri、离线资源和安装包的完整链路。

### 决策六：删去已经确认无价值的历史负担

**结论：** 对重复素材、占位包、旧分支、无用生成物和废弃运行形态及时清理。

**原因：** 降低维护噪声，确保仓库反映真实产品状态。

**影响：** 项目历史中多次出现大规模删除提交；删除是有依据的产品治理，而非功能倒退。

### 决策七：变更必须与项目文档同步（含项目志）

**结论：** 任何进入正式交付的变更完成后，版本标识、README、变更记录、MEMORY 与 `PROJECT_CHRONICLE.md` 同步更新。

**原因：** 2026-07-23 建档后，治理层落地与 v0.3.1、v0.3.2 三次提交均未同步项目志，导致线上项目志停留在 v0.3.0 并缺失两段历史；文档不同步会破坏项目史的可信性。

**影响：** 每次变更需检查项目志补录；本志本次补录即按此执行。

## 十四、走过但未保留的道路

### 14.1 旧 CustomTkinter 桌面端

它证明了早期业务流程可以在桌面运行，但界面、任务和业务逻辑耦合较重。2026-06-20 被完整移除，后来没有恢复，而是由 Tauri 桌面架构取代。

### 14.2 FastAPI 本地 Web 主入口

它推动了服务化和任务边界形成，但最终没有作为面向普通用户的交付形态保留。2026-07-07 转向 Tauri 时，Web 路由、模板和静态应用被删除。

### 14.3 对不明确输入做默认猜测

项目曾将未知课表类型默认当作某一类课表。随着可信度要求提高，这条策略被明确废止。

### 14.4 用单个输出文件掩盖解析问题

项目后期明确拒绝这种处理方式。一个错误输出应当成为解析器和流程改进的证据，而不是手工修补后被遗忘。

## 结语

空谷的历史并不是一条笔直路线。

旧桌面端被拆分，Web 端被建立；桌面端又被彻底删除，随后以完全不同的 Tauri 架构重建。项目从强调功能跑通，转向强调输入契约、真实样本、识别审计和质量复核。

这些转折并不互相否定。早期桌面端验证了业务，Web 化推动了分层，Web-only 迫使项目做减法，Tauri 重建解决了最终交付，真实样本审计则让空谷开始对结果负责。

截至 2026-07-23，空谷已经完成了从“多人课表处理程序”到“离线双课表合并与可信空课生成工具”的核心转变。下一段历史，将取决于质量治理和人工复核闭环能否正式落地。
